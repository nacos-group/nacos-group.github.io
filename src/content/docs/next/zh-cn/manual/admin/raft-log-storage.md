# Raft 日志存储

Nacos 的 Raft 协议支持 `rocksdb` 和 `file` 两种日志存储后端，默认使用 `rocksdb`。`file` 后端使用分段文件保存 Raft 日志，提供日志校验和重启恢复能力。

后端选择只影响 Raft 日志。Raft 元数据、快照存储和日志条目编解码仍使用 JRaft 默认实现，Raft 多数派提交和状态机应用语义保持不变。该配置不替代配置中心使用的 Derby 或外置数据库。

本文面向部署和维护 Nacos Server 的用户。配置与部署步骤适用于日常运维；文件格式和内部接口用于理解恢复行为及定位问题，不是新增的对外 API。

| 组件 | 选择 `file` 后的行为 |
| --- | --- |
| Raft 日志存储 | 使用 `FileLogStorage`，通过 Segment、Manifest 和 Index 管理日志。 |
| Raft 元数据存储 | 继续使用 JRaft 默认实现，保存任期、投票等元数据。 |
| Raft 快照存储 | 继续使用 JRaft 默认实现，配合状态机快照和日志裁剪。 |
| 日志条目编解码 | 继续使用 JRaft 默认 codec，编码结果再封装成文件日志记录。 |
| 复制、选主和多数派提交 | 继续由 JRaft 协议处理。 |
| 配置中心数据库 | 保持原有 Derby 或外置数据库配置。 |

默认 RocksDB 后端的选择和既有数据布局保持不变。是否使用文件后端，应结合目标环境的文件系统能力、同步写入开销和恢复演练结果判断；不能仅根据后端名称推断性能或资源占用。

## 1. 配置后端

### 1.1. 配置项

在 Nacos Server 的 `${nacos.home}/conf/application.properties` 中配置：

| 参数名 | 说明 | 默认值 |
| --- | --- | --- |
| `nacos.core.protocol.raft.data.log_storage_type` | 日志后端，取值为 `rocksdb` 或 `file`；去除首尾空白并忽略大小写。空串、纯空白或其他值会导致 Raft 初始化失败。 | `rocksdb` |
| `nacos.core.protocol.raft.data.sync` | 是否同步写入日志。使用 `file` 时必须为 `true`。 | `true` |
| `nacos.core.protocol.raft.data.sync_meta` | 传递给默认 Raft 元数据存储的同步选项。不能用它替代 `file` 所要求的 `sync=true`。 | `false` |

配置名中的 `data` 是 Raft 配置映射的一部分，不能省略。`nacos.core.protocol.raft.log_storage_type` 不等同于本页介绍的参数。

### 1.2. 使用文件日志后端

在全新部署的 Server 节点上配置：

```properties
nacos.core.protocol.raft.data.log_storage_type=file
nacos.core.protocol.raft.data.sync=true
```

`sync` 默认已经是 `true`，示例中显式写出该配置，便于部署时检查。不要为了降低写入延迟而将文件后端的 `sync` 改为 `false`。

### 1.3. 保留默认 RocksDB 后端

无需增加配置，也可以显式设置：

```properties
nacos.core.protocol.raft.data.log_storage_type=rocksdb
```

### 1.4. 参数组合与生效时机

| 后端配置 | `sync` | 结果 |
| --- | --- | --- |
| 未配置 | 未配置 | 使用 `rocksdb`，同步写入默认开启。 |
| `rocksdb` | `true` | 使用默认 RocksDB 后端并同步写入。 |
| `file` | 未配置或 `true` | 使用文件后端，按同步写入方式初始化。 |
| `file` | `false` | 初始化失败，报错 `File Raft log storage requires sync=true`。 |
| 空串、纯空白或不支持的名称 | 任意 | 初始化失败，抛出 `IllegalArgumentException`。 |

后端值会先去除首尾空白，再忽略大小写匹配，因此 `FILE` 与 `file` 等效；规范配置建议使用小写。未配置参数与显式配置空值的含义不同。

后端在 Raft 初始化时、Raft 运行时启动前选择，选定的工厂会应用于当前节点创建的每个 Raft Group，包括后续创建的 Group。不支持按 Group 单独选择，也不支持运行中热切换。修改配置文件不会使已经打开的日志存储自动更换实现。

`sync_meta` 是传递给默认元数据存储的选项。即使将它设置为 `true`，也不能使 `file` 与 `sync=false` 的组合合法。元数据和快照的最终同步语义仍由 JRaft 默认实现处理。

:::caution[已有节点不能通过修改配置迁移后端]
后端选择不会转换已有日志、元数据或快照。文件后端使用独立的 `file-log` 子目录，这种目录隔离不提供数据迁移能力。不要在已有节点上直接修改后端后重启，也不要把切回 `rocksdb` 当作数据回滚方式。升级已有集群时，保留原后端；在全新部署中启用 `file` 前，先验证文件系统能力和恢复行为。
:::

## 2. 存储目录

### 2.1. 目录布局与文件职责

每个 Raft Group 使用独立目录。文件日志存储布局如下：

```text
${nacos.home}/data/protocol/raft/<group>/
├── log/
│   └── file-log/
│       ├── LOCK
│       ├── manifest
│       ├── manifest.tmp
│       ├── segments/
│       │   └── 00000000000000000001.seg
│       └── index/
│           └── 00000000000000000001.idx
├── meta-data/
└── snapshot/
```

| 文件或目录 | 用途 |
| --- | --- |
| `LOCK` | 获取目录排他锁，防止多个存储实例同时打开同一目录。锁文件存在不代表锁仍被持有。 |
| `manifest` | 保存存储身份、Group 标识和本地有效日志范围；恢复时据此校验日志。该范围不等同于 Raft 多数派已提交范围。 |
| `manifest.tmp` | 发布新 Manifest 时使用的临时文件，通过原子替换更新 `manifest`。 |
| `segments/` | 保存带校验信息的分段日志文件。 |
| `index/` | 保存日志位置索引，初始化时扫描已发布日志重建。 |
| `meta-data/`、`snapshot/` | 由 JRaft 默认实现管理的元数据和快照目录。 |

备份时应先停止对应节点，再备份完整的 `data` 目录及配置，保持日志、元数据和快照一致。不要在运行中单独复制、替换或删除 Manifest、Segment 或索引文件，也不要混用不同 Group 或不同存储实例的文件。

### 2.2. Group 标识与存储身份

文件存储同时检查业务 Group 标识和本地存储身份：

- `groupId`：来自 JRaft 初始化上下文，必须与 Manifest 中保存的 Group 标识一致。
- `storeId`：首次创建 Manifest 时生成的 UUID，后续 Segment Header 必须使用同一身份。
- `segmentId`：Segment 的编号，Header 中的编号必须与 Manifest 描述或对应文件名匹配。

`storeId` 随文件持久化。复制整套存储文件会保留原身份，不会因为换了路径就自动生成新的身份。不要通过修改 Manifest 中的标识让一组文件冒充另一个 Group 或存储实例。

### 2.3. 文件编号与实现限制

Segment 和 Index 文件名使用补零到 20 位的 ASCII 十进制编号，后缀分别为 `.seg` 和 `.idx`。编号用于区分文件，不应直接解释为文件中第一条日志的 index。

初始化会在清理文件之前，结合 Manifest 与目录中的规范 Segment 文件名计算后续编号。被保留的未知归属 Segment 也参与计算，避免重用其编号；编号溢出会导致初始化失败。

| 项目 | 当前实现限制 | 说明 |
| --- | --- | --- |
| 文件格式版本 | `1` | Segment、日志记录和 Manifest 均包含格式版本。 |
| 单个 Segment | 128 MiB | 包含 40 字节 Header 和后续日志记录；容量不足时滚动创建新段。 |
| 单条文件日志记录 | 64 MiB | 包含 16 字节 Header、JRaft 编码后的 payload 和 8 字节校验值。 |
| 单个 Manifest | 16 MiB | 包含 Group 标识和全部有效 Segment 描述符。 |
| Group 标识 | UTF-8 编码后最多 1024 字节 | 必须非空白，并能正确编码。 |
| 单条 Index 记录 | 12 字节 | 8 字节记录 offset 和 4 字节记录总长度。 |

上述值是当前文件后端的实现边界，没有在本次变更中增加对应的用户调节参数。64 MiB 是封装后的单条日志记录上限，不能当作配置内容或 HTTP 请求允许达到该大小的承诺；请求和业务数据仍受各自限制。

## 3. 文件结构设计

文件后端由 Segment、Manifest 和 Index 三部分配合工作：Segment 保存日志记录，Manifest 定义当前有效的日志范围，Index 将日志 index 映射到 Segment 中的记录位置。理解这三者的关系，有助于区分已写入文件的数据、已发布的本地日志和可重建的辅助数据。

文件格式版本为 `1`，多字节数值使用大端序。以下偏移和长度均以字节为单位，区间采用左闭右开表示法。

### 3.1. Segment：分段日志文件

Segment 是日志记录的实际载体，存放在 `segments/` 目录中。每个文件由固定长度 Header 和连续追加的日志记录组成；单条记录完整地保存在一个 Segment 中，不跨文件拆分。

#### 3.1.1. 文件组织与滚动

单个 Segment 上限为 128 MiB，其中前 40 字节为 Header。追加时使用当前活动段；剩余容量不足以容纳下一条完整记录时，先刷盘并关闭旧段，再创建新段继续写入。一次批量追加可以跨越多个 Segment。

Segment 文件编号独立于日志 index。每个段实际保留哪些日志、从哪个字节开始读取、读取到哪里结束，都由 Manifest 的描述符决定。因此，文件中可能仍有已裁剪的前缀或尚未发布的尾部，不能仅根据文件名和物理长度确定有效日志范围。

#### 3.1.2. Segment Header

每个 Segment 以 40 字节 Header 开始，其后为日志记录：

| 偏移 | 长度 | 内容 |
| --- | --- | --- |
| 0 | 4 | magic：`0x4e4c5331`（`NLS1`）。 |
| 4 | 2 | 格式版本。 |
| 6 | 2 | Header 长度，固定为 40。 |
| 8 | 16 | UUID `storeId`，高 64 位在前、低 64 位在后。 |
| 24 | 8 | `segmentId`，必须大于 0。 |
| 32 | 8 | CRC64，覆盖 `[0, 32)`。 |

#### 3.1.3. 日志记录与校验

设 JRaft codec 编码后的 payload 长度为 `L`，总记录长度为 `24 + L`：

| 偏移 | 长度 | 内容 |
| --- | --- | --- |
| 0 | 4 | magic：`0x4e4c5231`（`NLR1`）。 |
| 4 | 2 | 格式版本。 |
| 6 | 2 | Header 长度，固定为 16。 |
| 8 | 4 | payload 长度 `L`。 |
| 12 | 4 | CRC32，覆盖 `[0, 12)`。 |
| 16 | `L` | JRaft 日志条目 payload。 |
| `16 + L` | 8 | payload 的 CRC64。 |

读取时先检查 Header、长度和记录边界，再分配 payload 缓冲区。解码后的日志 index 必须大于 0、term 非负、条目类型有效；配置条目还会校验成员信息。恢复扫描要求记录 index 与预期位置连续一致。

CRC32 使用 `java.util.zip.CRC32`，CRC64 使用 JRaft 的 `CrcUtil.crc64()`。Header 校验用于在读取 payload 前验证长度等信息，payload 校验用于检测记录内容损坏，Segment Header 中的身份校验则用于发现文件混用。

校验和用于发现损坏，不会自动修复记录。已发布范围内的记录校验失败时，恢复不能跳过该记录继续推进日志 index。

### 3.2. Manifest：有效日志范围与发布状态

Manifest 是当前本地日志范围的描述文件。它保存存储身份、Group 标识、全局首尾 index 和有序 Segment 描述符；日志恢复和读取均以这些范围信息为依据。

Manifest 中的“已发布”表示文件后端已经完成相应的本地范围更新。Raft 多数派提交、状态机应用和快照进度仍由上层协议管理，不能把 Manifest 的末尾 index 直接当作业务已经提交或应用的位置。

#### 3.2.1. Segment 描述符

每个 Segment 描述符由以下五个 8 字节整数构成：

| 字段 | 含义 |
| --- | --- |
| `segmentId` | 对应 Segment 文件的编号。 |
| `firstIndex` | 该段当前保留的第一条日志 index。 |
| `lastIndex` | 该段当前保留的最后一条日志 index。 |
| `firstRecordOffset` | 第一条保留记录在 Segment 中的字节偏移。 |
| `publishedEndOffset` | 已发布记录结束位置的下一字节偏移。 |

该段的有效字节范围为 `[firstRecordOffset, publishedEndOffset)`。描述符编号必须严格递增，日志范围必须连续，全局首尾 index 必须与描述符一致。前缀裁剪后，第一条有效记录可以位于 Segment Header 之后的更远位置；文件开头仍有旧记录不代表它们仍可读取。

空日志范围表示为 `[firstLogIndex, firstLogIndex - 1]`，此时没有 Segment 描述符。重置日志范围时会保留下次追加的起点，而不需要创建占位日志。

#### 3.2.2. Manifest 文件格式

Manifest 包含 52 字节固定 Header、UTF-8 Group 标识、有序 Segment 描述符和末尾 CRC64。设 Group 标识编码长度为 `G`、Segment 数量为 `N`，文件总长度为 `60 + G + 40N`。

| 偏移 | 长度 | 内容 |
| --- | --- | --- |
| 0 | 4 | magic：`0x4e4c4d31`（`NLM1`）。 |
| 4 | 2 | 格式版本。 |
| 6 | 2 | Header 长度，固定为 52。 |
| 8 | 4 | 文件总长度。 |
| 12 | 16 | UUID `storeId`，高 64 位在前、低 64 位在后。 |
| 28 | 8 | `firstLogIndex`。 |
| 36 | 8 | `lastLogIndex`。 |
| 44 | 4 | Group 标识的 UTF-8 字节数 `G`。 |
| 48 | 4 | Segment 描述符数量 `N`。 |
| 52 | `G` | UTF-8 Group 标识。 |
| `52 + G` | `40N` | 有序 Segment 描述符。 |
| `52 + G + 40N` | 8 | 此前全部字节的 CRC64。 |

读取 Manifest 时会检查文件长度、格式版本、Header、校验和、Group 编码及日志范围。Group 标识必须非空白且 UTF-8 编码长度不超过 1024 字节；不支持的版本、非法编码、大小不符或范围不连续均不能作为有效 Manifest 使用。

#### 3.2.3. 正式文件与临时文件

`manifest` 保存当前发布状态，`manifest.tmp` 用于准备下一次更新。发布时先写入并刷盘临时文件，再通过同目录原子替换更新正式文件，具体顺序见第 4 节。

临时文件可能因异常退出而留下。它的存在本身不能证明上一次操作已经成功，也不能替代正式 Manifest 作为恢复依据。恢复时由存储实现验证正式文件及其引用的数据，再决定后续清理。

### 3.3. Index：可重建的位置索引

Index 存放在 `index/` 目录中，与对应 Segment 使用相同编号。它将日志 index 映射为记录的物理位置，避免每次读取都从 Segment 开头顺序扫描。

#### 3.3.1. 索引布局与槽位计算

Index 没有文件头，每条索引记录占 12 字节：

| 记录内偏移 | 长度 | 内容 |
| --- | --- | --- |
| 0 | 8 | 日志记录在 Segment 中的字节 offset。 |
| 8 | 4 | 日志记录总长度，包括 Header、payload 和校验值。 |

以该段第一条保留日志为 `baseIndex`，目标日志的索引槽位偏移为 `(logIndex - baseIndex) × 12`。例如，`baseIndex=100` 时，日志 `index=102` 的索引记录位于 `.idx` 文件的第 24 字节处；该索引记录中保存的 offset 才是日志在 `.seg` 文件中的位置。

索引文件长度必须与该段保留的条目数量一致。计算槽位、记录结束位置和后续 index 时会进行溢出检查，避免损坏的数值越过文件边界。

#### 3.3.2. 日志读取流程

读取一条日志时，存储依次执行：

1. 根据 Manifest 的全局范围检查目标 index；范围外不会继续查找记录。
2. 在有序 Segment 描述符中定位包含目标 index 的段，确定该段的保留范围。
3. 读取 Index 槽位，检查记录长度及其字节范围是否处于 Manifest 发布范围内。
4. 从 Segment 读取记录，校验 Header、payload 校验和及编码，并确认解码后的 index 与请求 index 一致。

因此，仅修改 Index 不能扩大有效日志范围；Index 中的 offset 和长度也不能绕过 Segment 记录本身的校验。

#### 3.3.3. 索引重建与维护

Index 是由 Segment 派生的数据。初始化时会扫描所有已发布 Segment，按照经过校验的保留记录重建索引；前缀裁剪等操作也会根据新的边界调整或重建索引。

追加过程中会同步更新 Index，但本地发布顺序不依赖 Index 刷盘。持久化与恢复所需的日志内容及有效范围由 Segment 和 Manifest 共同确定。

可以重建不等于可以在运行中定期删除 Index 节省空间。运行中的存储仍然持有活动索引资源，文件回收由实现管理；手工删除、拼接或替换文件可能破坏资源与磁盘状态的一致性。

## 4. 持久化设计

文件后端通过“先写入并刷盘日志，再发布 Manifest 范围”的顺序组织持久化。追加、裁剪和重置都围绕这一发布边界执行，失败后的处理则根据操作是否已经进入实际文件变更阶段区分。

### 4.1. 本地发布与一致性边界

持久化过程需要区分三个层次：

| 层次 | 含义 |
| --- | --- |
| Segment 中已有记录 | 记录字节已经写入文件，可能仍位于尚未发布的尾部。 |
| Manifest 已发布范围 | 文件后端已经更新本地有效范围，恢复会验证该范围引用的记录。 |
| Raft 多数派提交与状态机应用 | 由 JRaft 的复制、提交和应用流程决定业务可见结果。 |

Manifest 不以文件中最大的 index 或 Segment 的物理长度推导有效范围，而是显式保存保留范围和字节边界。这样，恢复能够识别未完成的追加，也能够在范围更新后继续完成尚未结束的裁剪与回收。

日志 index、Segment 编号和文件偏移均进行边界与溢出检查。校验失败时不应通过扩大 Manifest 范围或调整 Index 来绕过限制。

### 4.2. 批量追加与原子发布

文件后端先校验整批日志，再写入文件。校验包括：日志 index 必须从当前末尾的下一个位置连续递增，每条记录能放入空 Segment，计划中的 Manifest 满足格式和大小限制。

批次校验通过后，按以下顺序执行：

1. 将日志记录追加到活动 Segment，同时写入 Index。
2. Segment 容量不足时，刷盘旧段并滚动创建新段；批次写入结束后刷盘最后一个 Segment。
3. 新 Manifest 引用了新增 Segment 时，同步 `segments` 目录。
4. 写入 `manifest.tmp`，并对临时文件执行 `force(true)`。
5. 使用同目录的原子移动替换 `manifest`。
6. 同步 `file-log` 目录，更新内存中的 Manifest，完成本地范围发布。

目录同步遵循第 4.4 节及第 4.6 节的平台规则。Index 是派生数据，发布顺序不依赖其刷盘；恢复时通过扫描已发布 Segment 重建。

日志记录出现在 Segment 文件中，并不意味着它已经被 Manifest 发布；Manifest 发布完成，也不等于日志已经由 Raft 多数派提交或应用到状态机。业务操作是否成功，应依据上层协议和业务接口的结果判断。

### 4.3. 范围变更、日志裁剪与快照

快照和复制冲突处理可能触发前缀裁剪、后缀裁剪或日志范围重置。以下是 JRaft 内部存储接口的语义，不需要用户通过 HTTP 或 SDK 主动调用：

| 内部操作 | 保留范围与行为 |
| --- | --- |
| `truncatePrefix(firstIndexKept)` | 保留目标 index 及之后的日志；目标超过原末尾时，发布从目标开始的空范围。 |
| `truncateSuffix(lastIndexKept)` | 保留目标 index 及之前的日志；目标低于原首 index 时，发布以原首 index 开始的空范围。 |
| `reset(nextLogIndex)` | 发布 `[nextLogIndex, nextLogIndex - 1]` 的空范围，后续从目标位置继续追加，不创建占位日志。 |

这些操作先发布新的 Manifest 范围，再处理边界段、索引和失效文件。被移除的日志及配置条目不能继续读取。快照中的 index、term 和成员信息仍通过 JRaft 的快照及 LogManager 路径承接。

不能通过手工删除旧 `.seg` 文件代替日志裁剪。磁盘上暂时仍有失效文件，也不表示它们仍属于有效日志范围，应以 Manifest 和恢复校验结果为准。

裁剪边界位于已保留范围内时，会先读取并校验边界记录，再发布新 Manifest。发布后才调整边界段与索引、重开活动资源并回收失效文件；重启恢复也遵循已经验证的发布范围。

文件后端保留 JRaft 的快照存储与快照处理路径。周期性快照仍用于状态恢复和日志裁剪，不能用更换日志后端或手工删除 Segment 来代替快照。

### 4.4. 文件与目录的同步要求

文件后端要求数据路径所在文件系统支持：

- 排他文件锁，同一目录只能由一个存储实例打开。
- 普通文件同步刷盘，日志与临时 Manifest 使用 `force(true)`。
- 同目录内的 Manifest 原子替换。
- 非 Windows 平台上的目录同步刷盘。初始化还会同步 `file-log` 的祖先目录，需要目标运行环境支持这些操作。

Segment、Manifest 和相关目录会执行文件类型检查；要求普通文件或真实目录的路径不能用符号链接替代。必要的锁、刷盘或原子替换操作失败，会导致初始化或写入失败。

目录同步按照 `segments`、`index`、`file-log` 及其全部祖先目录的顺序执行，即使这些目录已经存在也会调用同步入口。非 Windows 平台会实际打开目录并执行 `force(true)`；因此，仅确认数据目录可以创建文件并不足以证明环境满足要求。

### 4.5. 并发控制与目录互斥

同一存储实例使用读写锁协调访问。日志读取在读锁内完成定位、校验和解码；追加、裁剪、重置和关闭在写锁内执行，避免读者观察到一条只更新了部分内容的记录。

不同存储实例之间通过 `LOCK` 文件上的 `FileChannel.tryLock()` 获取目录排他锁，防止同时打开同一目录。操作系统管理的是文件通道上的锁状态，锁文件是否存在与锁是否仍被持有需要分别判断。

正常关闭会关闭活动 Segment 和 Index、释放目录锁并清空运行状态。必要写入失败后即使活动写入资源已关闭，目录锁也会继续保留到存储关闭；不能通过删除 `LOCK` 文件启动另一个进程绕过互斥。

### 4.6. Windows 的持久性边界

:::caution[Windows 持久性限制]
Windows 会在校验目录后自动跳过目录同步，没有额外的配置开关；普通文件刷盘、排他锁和 Manifest 原子替换仍然必需。每次实际初始化成功时会记录一条包含存储路径的 WARN，说明跳过目录同步的影响。

Windows 下不能保证依赖目录同步屏障的断电恢复：已确认的本地日志范围可能丢失，Manifest 与截断或回收结果不一致时可能恢复失败。进程强杀后的恢复验证不能证明操作系统崩溃或断电后的安全性。
:::

Windows 的 WARN 在每次实际初始化成功时输出；已经持锁时的幂等初始化和普通追加不会反复输出。跳过目录同步不意味着可以关闭 `sync`，也不意味着文件刷盘或原子替换失败会被忽略。

## 5. 异常恢复

异常恢复以原目录中的正式 Manifest 和日志文件为依据，先验证发布范围及数据身份，再处理未发布尾部和可回收文件。已经发布的数据缺失或损坏时，存储会拒绝初始化，避免把不完整的日志当作有效状态继续使用。

### 5.1. 初始化与恢复顺序

节点重新打开原目录时，会获取排他锁，校验 Manifest、存储身份、日志校验和及连续范围，并重建索引。通过恢复校验后，才会截断未发布的尾部并清理可回收文件。已发布日志缺失、损坏、范围不连续或身份不匹配时，初始化失败，不会跳过这些日志继续运行。

具体过程如下：

1. 校验同步写入选项、Group 标识、配置管理器和日志 codec。
2. 创建并校验根目录，获取 `LOCK` 排他锁，创建和同步所需子目录及祖先目录。
3. 读取并验证 Manifest；首次初始化时，在确认目录满足空存储要求后创建 Manifest。
4. 在清理前计算 Segment 编号高水位，确保后续分配不重用已识别的编号。
5. 扫描 Manifest 发布范围内的所有记录，校验 Header、校验和、身份及 index 连续性，重建 Index，并收集 Raft 配置条目。
6. 检查未被 Manifest 引用的 Segment，区分可回收文件、需要保留的文件和必须报错的文件。
7. 同步已验证 Manifest 所在目录，建立恢复屏障；Windows 按平台规则仅校验目录并跳过同步。
8. 截断已发布 Segment 的未发布尾部并刷盘，回收失效 Segment、无用 Index 和临时 Manifest。
9. 重开活动资源，将配置条目恢复到 JRaft 配置管理器，确认资源完整后完成初始化。

在恢复屏障之前，已有 Manifest 和 Segment 保持原状；派生 Index 可以重建。这里的“恢复屏障”指后续清理前对已验证 Manifest 目录项执行的同步步骤，不能据此扩大 Windows 的断电持久性保证。

### 5.2. Manifest 缺失与临时文件残留

没有 Manifest 时，仅允许存在空的 `segments`、`index` 子目录、普通 `LOCK` 文件和普通临时 Manifest。满足条件后会创建空存储；如果日志或索引目录已有内容，或者根目录出现其他不允许的文件，初始化失败。

这项检查用于避免把缺少 Manifest 的历史目录误认为全新目录。不要通过清空目录、新建空 Manifest 或把 `manifest.tmp` 手工改名来绕过检查。应先保留现场，再确认目录来源及完整备份。

当正式 Manifest 存在且通过验证时，残留的临时文件由恢复流程在适当阶段清理；不能根据 `manifest.tmp` 的时间戳或文件大小推断发布已经完成，也不应手工将其提升为正式文件。

### 5.3. 未引用 Segment 的分类处理

下表适用于 `segments` 中具有规范文件名、但未被 Manifest 引用的文件：

| 检查结果 | 恢复行为 |
| --- | --- |
| Header 有效，`storeId` 属于当前存储，编号与文件名匹配 | 在恢复屏障之后可以回收。 |
| 普通文件 Header 不完整，或 magic、Header 长度、Header 校验损坏 | 原地保留并记录包含路径的 WARN，继续校验已发布日志。 |
| Header 属于其他 `storeId`、编号与文件名不符、版本不支持或身份非法 | 初始化失败。 |
| 非普通文件、符号链接或实际 I/O 错误 | 初始化失败。 |

无法确认归属的文件不会被重放，其规范文件名仍参与后续编号计算。保留 WARN 不表示对应内容已经进入有效日志范围，也不表示可以忽略其他恢复错误。

### 5.4. 不同中断阶段的恢复依据

进程可能在一次操作的不同阶段退出。下表说明恢复的判断依据；其中涉及目录同步的步骤仍受第 4.6 节的 Windows 限制约束。

| 中断阶段 | 重启后的处理依据 |
| --- | --- |
| 日志已写入，但新 Manifest 尚未替换正式文件 | 以已验证的正式 Manifest 为准；发布范围外的尾部或未引用文件按恢复规则处理。 |
| 临时 Manifest 已写入或刷盘，但尚未原子替换 | 不因临时文件存在就认定新范围已发布，仍校验正式 Manifest。 |
| Manifest 已原子替换，但目录同步或后续资源操作失败 | 磁盘可能已经存在新 Manifest；恢复以实际读取并验证后的状态为准，不能根据失败响应手工回退文件。 |
| 新范围已发布，但边界截断或失效文件回收尚未完成 | 先验证新范围、执行恢复屏障，再处理未发布尾部和可回收文件。 |
| 已发布范围内的文件缺失、记录损坏或身份不匹配 | 初始化失败，不会跳过损坏记录或自动混用其他存储文件。 |

进程退出测试只覆盖进程故障，不能直接证明操作系统崩溃或断电时目录项和数据都已持久化。恢复演练需要区分这些故障模型。

### 5.5. 运行时失败状态与后续操作

| 失败类型 | 存储行为 | 运维含义 |
| --- | --- | --- |
| 参数、编码或批次规划校验失败 | 在写入本批文件前拒绝操作，存储仍可继续使用。 | 检查调用内容或大小边界，不应直接认定磁盘故障。 |
| 实际变更中的必要 I/O 或资源重开失败 | 关闭活动 Segment 和 Index，禁止后续追加、裁剪和重置。 | 需要处理底层故障，再关闭并重新打开存储。 |
| 读取 I/O 或解码失败 | 记录包含目录、index 和异常的 ERROR，读取返回失败结果。 | 检查数据完整性和异常链，不要把读取失败当作正常缺失。 |
| 失效文件删除或回收后的目录同步失败 | 记录 WARN，已发布范围保持有效。 | 关注磁盘空间和持续回收失败，避免失效文件长期积累。 |

实际日志变更中发生必要 I/O 或资源重开失败后，目录锁仍保留到关闭。处理底层故障后，应先停止节点以释放资源，再使用原后端和原目录重启，触发恢复校验。持锁期间重复调用初始化只检查当前状态，不会重新执行恢复流程。

写入返回失败时，磁盘上可能已经存在新的 Manifest，重启后以磁盘校验结果为准；不要根据一次失败响应手工回退文件。失效文件回收失败会记录 WARN，不改变已发布日志范围。

### 5.6. 常见错误与排查方向

排查时先查看 `${nacos.home}/logs/protocol-raft.log` 中的路径和异常信息。后端取值和同步选项校验失败时，还应检查服务端启动日志。

| 错误或日志消息 | 含义与处理 |
| --- | --- |
| `Invalid nacos.core.protocol.raft.data.log_storage_type` | 后端值非法，检查是否为 `rocksdb` 或 `file`。 |
| `File Raft log storage requires sync=true` | 文件后端关闭了同步写入，修正配置后重启。 |
| `File log directory is already in use` | 无法取得目录排他锁，检查是否有其他进程或实例使用同一数据目录。删除 `LOCK` 文件不能替代释放锁。 |
| `Manifest is missing with existing data` | Manifest 缺失，但日志或索引目录非空。保留现场并检查完整备份，不要通过新建空 Manifest 绕过校验。 |
| `Unexpected content without a manifest` | 缺少 Manifest 的根目录存在不允许的内容，检查是否指定了错误路径或混入其他文件。 |
| `Manifest group does not match JRaft group` / `Segment identity does not match manifest` | Group 或存储身份不一致，检查是否混用了数据文件。 |
| `Foreign segment in file log directory` | 未引用 Segment 的有效 Header 属于其他存储，不能自动回收，需检查目录来源。 |
| `Segment id does not match its file name` | Segment Header 的编号与文件名不符，检查是否手工改名或混入了文件。 |
| `Published record is incomplete` / `Non-contiguous log index` | 已发布范围内存在不完整记录或 index 不连续，保留现场并检查数据完整性。 |
| `File log record header checksum mismatch` / `File log record payload checksum mismatch` | 记录 Header 或 payload 校验失败，不能通过跳过该记录恢复。 |
| `Segment ID exhausted` / `File ID overflow` | Segment 编号无法继续分配，或规范文件名中的编号超出 long 范围。 |
| `Preserving unpublished segment with unknown ownership` | 保留了无法确认归属的未发布 Segment；该文件不会被重放，已发布日志仍需通过校验。 |
| `Failed to initialize file log storage` | 查看后续异常，检查文件系统能力、权限、磁盘空间和数据完整性。 |

对于底层文件系统异常，还应查看异常链中的具体操作和路径，例如锁获取、目录打开、文件刷盘、原子移动或截断失败。不要仅根据最外层的初始化失败消息判断数据一定已经损坏。

### 5.7. 必要写入失败后的恢复步骤

1. 保存故障时间、节点和 Group 信息，收集完整异常链及相关路径。
2. 按集群流程停止故障节点，保留原目录，不要先清空文件或切换后端。
3. 检查磁盘空间、权限、挂载状态及所需文件系统能力，处理已经定位的底层问题。
4. 使用原版本对应的后端配置和原目录启动，让存储执行完整恢复校验。
5. 恢复成功后验证业务读写、集群追平和后续写入；若仍出现已发布数据缺失、损坏或身份不匹配，应保留现场并结合完整备份、集群状态制定恢复方案。

数据校验失败没有通用的“删除某个文件即可修复”步骤。不要编辑校验值、手工拼接不同副本的文件，或把内部 `reset` 接口当作修复已损坏日志的运维命令。

遇到目录占用时，还应先确认原进程已经退出并释放文件通道，再使用原后端和原目录重启。不要把删除锁文件、切换日志后端或重复调用初始化当作释放资源与执行恢复的替代方式。

## 6. 部署与运维排查

本节以发行包部署为例，说明如何启用文件后端、确认配置生效，以及遇到启动或运行故障时从哪里开始排查。以下 shell 命令在 Linux 环境的 `${nacos.home}` 目录执行；容器部署应在实际运行 Nacos Server 的容器内检查对应配置、挂载路径和日志。

### 6.1. 准备部署环境与数据目录

使用包含文件日志后端实现的 Nacos 版本，先按[单机部署](./deployment/deployment-standalone.mdx)或[集群部署](./deployment/deployment-cluster.md)完成数据库、节点列表和鉴权配置。文件日志参数只决定 Raft 的日志实现，不替代这些部署配置。

启用前确认以下事项：

1. 这是全新部署，或者节点原本就使用 `file` 后端；已有 RocksDB 节点不要通过修改配置原地切换。
2. 每个 Server 节点使用独立的数据目录，不与其他进程共用同一套 Group 文件。
3. Nacos 运行用户对数据路径具有创建、读取、写入、截断、重命名和删除文件所需的权限。
4. 实际数据路径支持第 4.4 节要求的文件锁、文件刷盘和原子替换；非 Windows 平台还需要目录及祖先目录同步。

使用容器或挂载卷时，配置文件需要挂载到 Server 实际读取的位置，数据卷需要保留原节点的数据路径。应在相同运行用户和挂载方式下检查这些条件，不能只根据宿主机上的权限判断。

### 6.2. 配置并启动 Server

在每个 Server 节点的 `conf/application.properties` 中加入：

```properties
nacos.core.protocol.raft.data.log_storage_type=file
nacos.core.protocol.raft.data.sync=true
```

集群模式需要先按部署手册配置各节点的 `conf/cluster.conf`，然后在每个节点启动：

```shell
bash bin/startup.sh -m cluster
```

开发或测试环境使用单机模式时，启动命令为：

```shell
bash bin/startup.sh -m standalone
```

如果采用控制台独立部署，可在 Server 启动命令中增加 `-d server`，具体步骤见[控制台独立部署](./deployment/deployment-independent.md)。文件后端参数应配置在 Server 一侧，修改独立 Console 的配置不会替换 Server 的日志存储。

后端选择在 Raft 初始化时生效。配置修改后，仅保存文件不会改变已经打开的存储实例；已使用文件后端的节点需要按既有运维流程重启，才能重新读取启动配置。

### 6.3. 确认文件后端已经生效

启动后按以下顺序检查：

1. 查看启动脚本输出的日志路径。发行包脚本默认将启动输出写入 `logs/startup.log`；检查是否存在配置校验或组件启动异常。
2. 查看 `logs/protocol-raft.log`，确认对应 Group 没有文件存储初始化失败、目录占用或数据校验错误。
3. 对已经创建的 Raft Group，检查其 `log/file-log/manifest` 是否存在。将下面路径中的 `<group>` 替换为实际 Group 名称。

```shell
tail -n 100 logs/startup.log
tail -n 100 logs/protocol-raft.log
ls -la "data/protocol/raft/<group>/log/file-log/"
```

Group 尚未追加日志时，`segments/` 可以为空。配置文件中存在 `file`、目录已经创建或进程仍在运行，都不足以单独说明业务写入已经成功。

通过实际经过 Raft 的持久化操作写入并读取数据，例如通过管理接口注册并查询持久实例，相关说明见[实例生命周期](../user/naming/instance-lifecycle.md)。再检查对应 Group 是否产生 `.seg` 和 `.idx` 文件；仅注册临时实例不能验证这条日志路径。

检查服务就绪状态的方法见[监控手册](./monitor.md)。如果节点尚未创建对应 Group，应先确认相关业务组件是否已经启用或初始化，不要手工创建日志文件来补齐目录。

### 6.4. 按故障现象排查

先记录故障节点、发生时间、受影响的 Group 和完整异常链，再按下表检查。具体错误消息及含义见第 5.6 节。

| 故障现象 | 先检查什么 | 后续处理 |
| --- | --- | --- |
| 启动时提示后端配置非法，或要求同步写入 | 确认 Server 实际读取的配置中使用完整参数名，后端为 `file`，且 `sync` 没有被其他配置来源覆盖为 `false`。 | 修正配置后重启；`sync_meta=true` 不能替代 `sync=true`。 |
| 提示目录已经被占用 | 检查是否存在另一个 Nacos 进程，或多个容器、节点挂载了同一数据目录。 | 停止占用同目录的实例并确认资源释放，不要删除 `LOCK` 绕过文件锁。 |
| 初始化、刷盘、原子移动或截断失败 | 根据异常中的实际路径，检查运行用户权限、磁盘空间、挂载状态及文件系统是否支持相应操作。 | 处理底层问题后，使用原后端和原目录重启；检查恢复结果。 |
| Manifest 缺失、记录校验失败或存储身份不匹配 | 检查是否误删文件、只恢复了部分备份、混用了其他 Group 的文件，或启动时指向了错误目录。 | 保留原目录与日志，按第 5.7 节处理；不要新建 Manifest、修改校验值或拼接其他副本的文件。 |
| 写入失败后，后续写入也持续失败 | 检查首次失败的异常，而不只查看最后一次请求；必要 I/O 失败会关闭活动写入资源。 | 处理底层故障后停止并重新启动节点，触发完整恢复；仅重试业务请求不会重新打开存储。 |
| 日志持续出现失效文件回收 WARN，磁盘空间不断减少 | 检查异常中的文件路径、删除权限和磁盘状态，区分回收失败与已发布数据损坏。 | 修复回收失败的原因，由存储管理文件；不要按文件名自行删除 Segment。 |
| 只出现 Windows 目录同步 WARN | 确认消息说明的是平台跳过目录同步，而不是文件刷盘或初始化失败。 | 按第 4.6 节理解断电持久性边界；继续确认节点和业务状态。 |

Linux 下排查磁盘空间和目录权限时，可以在故障节点执行以下只读命令：

```shell
df -h data
df -i data
ls -ld data data/protocol data/protocol/raft
```

容器中应检查实际挂载的数据卷；若故障路径尚未创建，则检查它最近的已存在父目录。目录权限输出只能帮助定位问题，不能证明锁、刷盘或原子替换一定可用，仍需结合具体异常判断。

问题处理后，使用原后端和原数据目录启动节点，确认恢复不再报错、业务读写恢复，并检查该节点是否正常参与集群。恢复仍然失败时保留现场，结合完整备份与其他节点状态制定处理方案。需要执行快照或主动转移 Leader 时，使用现有[运维 API](./admin-api.md)。

## 7. 常见问题

### 7.1. 已有 RocksDB 节点能否改成 `file` 后重启？

不能把修改配置后重启当作迁移方法。后端选择不会转换日志、元数据或快照，本次能力没有提供 RocksDB 与文件后端之间的数据转换工具或在线迁移流程。

已有节点改用 `file` 会使用另一套日志文件，再切回 `rocksdb` 也不会把期间的数据合并回原日志。升级已有集群时应保留原后端；已经使用 `file` 的部署还需确认目标版本支持该实现及文件格式。其他版本升级限制见[升级手册](./upgrading.mdx)。

### 7.2. 能否只为一个 Raft Group 开启文件后端？

不能。当前后端工厂由 Server 初始化时统一选择，再应用到该节点创建的每个 Group，没有按 Group 指定后端的配置。

### 7.3. 为什么设置 `sync_meta=true` 之后仍然无法启动？

文件后端单独要求日志 `sync=true`。`sync_meta` 是传递给默认元数据存储的选项，不能替代日志同步条件。检查完整的 `nacos.core.protocol.raft.data.sync` 配置及其实际生效值。

### 7.4. `LOCK` 文件还在，是否说明上次进程没有退出？

不能只根据文件是否存在判断。锁状态由文件通道及操作系统管理，正常关闭释放的是锁，不要求删除锁文件。应检查是否仍有进程使用目录，不要通过删除 `LOCK` 启动第二个存储实例。

### 7.5. 看到 `manifest.tmp` 是否说明恢复失败？

不一定。它是发布 Manifest 时使用的临时文件，异常退出可能留下该文件。是否能够恢复，应以正式 Manifest、Segment 和恢复校验结果为准；不要手工把临时文件改名为正式 Manifest。

### 7.6. Index 可以重建，能否定期删除以节省空间？

不应这样维护。恢复会重建索引，但运行中的存储仍然使用活动 Index。手工删除、替换或拼接索引文件可能破坏资源与磁盘状态的一致性，文件回收应由存储实现管理。

### 7.7. 使用文件后端后，还需要快照吗？

需要。文件后端只替换日志存储，快照仍用于状态恢复和日志裁剪，JRaft 的快照处理路径保持不变。不能通过手工删除 Segment 代替快照或日志裁剪。

### 7.8. 备份时需要保存哪些文件？

先按集群运维流程停止待备份节点，确认进程退出并释放资源，再保存该节点完整的 `data`、`conf`、成员配置和版本信息，使日志、元数据、快照和部署配置来自一致的停机状态。维护集群时应保留所需的多数派可用性。

仅备份 `segments`、仅保留最新 Segment，或者只复制 Manifest 都不足以构成完整节点备份。配置中心使用外置数据库时，还需按数据库自身流程备份，Raft 文件备份不能替代数据库备份。备份恢复应在隔离环境中确认 Group 身份和业务数据符合预期。

### 7.9. Windows 的目录同步 WARN 能否通过关闭 `sync` 消除？

不能。Windows 会按平台策略跳过目录同步，没有额外的开关；普通文件刷盘、文件锁和原子替换仍然必需。关闭 `sync` 会使文件后端初始化失败，也无法弥补跳过目录同步带来的断电持久性限制。
